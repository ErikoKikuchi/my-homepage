## D-001 マルチDB構成(thinkmotion_db / client_db / code_db)

- **決定**: アプリケーションごとにDBを分離する(`thinkmotion_db`をデフォルト、`client_db`をPilates用、`code_db`をCode用として確保)
- **背景**: 「構造化セルフケアプラットフォーム」として複数アプリケーション(Pilates / ThinkMotion / Code / Admin)を持つ構成のため、データの責務を明確に分けたい
- **理由**: 各アプリケーションの成長速度・スキーマ変更頻度が異なることが見込まれるため、DBレベルで分離しておくと将来の切り出し(マイクロサービス化やアプリごとの独立運用)がしやすい
- **トレードオフ**: JOINを跨いだ集計ができない。`users`テーブルの共有方法(D-002)で一部緩和

### D-002 認証ガード間のリダイレクト設計(2026-07-06)

- **背景**:
  Laravel 12でトップページをLaravel側に移行し、pilates/thinkmotion/adminの3セクションを
  ミドルウェアで保護する構成に変更した。未ログイン時のリダイレクト先制御と、
  ログイン後の遷移先復元が必要になった。

- **決定1**: `intended()`は不採用
  理由:
- `url.intended`はセッション内の単一キーであり、ガード(pilates/thinkmotion/admin)を
  跨いで共有されるため、複数ガード運用下で意図しない遷移先に解決される事故が過去に多発した。
- `SESSION_DOMAIN=null`によりサブドメイン間(pilates.localhost ⇔ thinkmotion.localhost)の
  セッションは分離されたが、同一ホスト内(例: pilates.localhost 一般 ⇔ pilates.localhost/admin)
  では依然として`url.intended`が共有されるリスクが残る。
- 上記により、Laravel標準の`intended()`機構には依存しない方針とする。

- **決定2**: `login_from`方式を採用、キーはセクション単位で分離
- ログイン画面表示時(GET)に、遷移元を示す`from`クエリをセッションに保存し、
  ログイン成功時(POST)に`pull()`して遷移先を`match`で決定する。
- セッションキーは`login_from`の単一共有をやめ、`pilates_login_from` /
  `thinkmotion_login_from`とセクションごとに分離。将来adminにも同様のゲスト
  リダイレクトを実装する場合は`admin_login_from`のように追加する。
- 任意のURLをパラメータとして受け渡す方式(オープンリダイレクトのリスクを伴う)は
  採用せず、遷移先はコード内の固定パターン(`match`)に限定する。

- **決定3**: `bootstrap/app.php`でのゲストリダイレクト制御
- Laravel 11以降の構成に合わせ、`Authenticate`ミドルウェアの個別実装ではなく
  `withMiddleware()`内の`redirectGuestsTo()`でパスベースにリダイレクト先を分岐
  (admin / thinkmotion / pilates)。

- **トレードオフ**:
- pilates admin機能は未実装。実装時は`showPilatesForm`と同様の`login_from`保存処理を
  admin側にも用意し、共通の`login`メソッド側でガード種別によって`pull()`対象キーを
  出し分ける必要がある。
- 本番環境でパスベースルーティング(`karada.sanpo/pilates`等、同一ホスト)に移行する際は、
  セクション間のセッション分離がSESSION_DOMAINに依存しなくなるため、この設計の
  再確認が必要。

### D-003 nginx単一ホスト統合

- **決定**:localhost単一ホスト配下に /pilates・/thinkmotion・/pilates/admin・/thinkmotion/admin・/codeをパスベースで配置。サブドメイン（pilates.localhost等）は廃止。
- code（ワールド・クック・クエスト構想）はパスの器だけ用意し、実装は将来着手時に着手する。
- **ハマった点と対処**:

.php用locationをlocation ~ ^/(pilates|thinkmotion|code)内にネストすると、内部リライト後のURI（/index.php）が正規表現に再マッチせずlocation /（static側）にフォールバックしてしまう。→ .php用locationをトップレベルの独立ブロックに分離して解決。
public/直下を絶対パスで参照している箇所（/js/components/_.js、/css/style.css、/images/_.png）が、単一ホスト化後はlocation /（static側dist）にフォールバックし404になっていた。→ /js/・/css/・/images/をLaravel側public/に振るlocation ^~ブロックを追加して解決。

- **注意**:nginx単一ホスト化時は、public/直下への絶対パス参照が静的サイト側にフォールバックしやすい。同様の統合を行う際はgrep -rn 'src="/\|href="/' resources/viewsで事前に洗い出すこと。

### D-004 環境変数

- **決定**:Laravel側 .env：THINKMOTION_URL / PILATES_URL を http://localhost に統一（旧: http://thinkmotion.localhost 等）。ホスト名＋パス付与（${url}/thinkmotion等）という既存のテンプレート構造は変更していない。
- STATIC_URL=http://localhost:5173 はVite dev server用のため変更不要（nginx統合はLaravel側の話であり、開発用HMRサーバーとは無関係）。
- static側 .env：VITE_THINKMOTION_URL / VITE_PILATES_URL も同様に http://localhost に統一。
- Windows側 hosts ファイルから pilates.localhost / thinkmotion.localhost のエントリを削除。code.localhost は将来のため残置。
- WSL2 + Docker Desktop環境のため、ブラウザ（Windows側）の名前解決はWindows側のhostsファイルに依存する点に注意。WSL側の/etc/hostsは自動生成されるため編集しても再起動で消える。

### D-A-001 usersテーブルの共有

- **決定**: Pilates / ThinkMotionで登録入口(フォーム・フロー)は完全に分けるが、`users`テーブルは1つに統合する
- **背景**: アプリケーションとしては別サービスとして扱い、ユーザーが混同しないよう入口を分離する。内部的には同一テーブルでフラグにより制御する。
- **理由**: テーブルを分けると将来的な名寄せや横断管理が困難になるため統合を選択。ただし両サービスを同一メールで利用するケースは想定しない。
- **制約**:
  - users.email にUNIQUE制約
  - 登録フォームはサービス選択ラジオボタン1画面に統合（Pilates / ThinkMotion）選択結果でフラグを振り分け
  - Pilates選択 → is_pilates_user = true
  - ThinkMotion選択 → is_medicalはプロフィール記入・管理者承認後にtrue（登録時点ではfalse）
  - 両方利用したい場合は管理者に連絡（アプリ側では考慮しない）
- **トレードオフ**: `users`テーブルはデフォルトDB（`thinkmotion_db`）に配置。
  Pilates側からの参照はクロスDB接続（`client_db`の接続設定でも`users`は`thinkmotion_db`を参照）になるため、
  Laravelのコネクション設定で明示的に`connection('mysql')`を指定する必要がある。

### D-A-002 ログインページの分離

- **決定**: ログインページをサービスごとに分離する
  - `/pilates/login`
  - `/thinkmotion/login`
- **理由**: 視覚的に別サービスと認識できるようにし、ユーザーの混乱を防ぐ
- **実装方針**:
  - 配色・見出し文言をサービスごとに変える（例: Paper系 / Forest系）
  - 認証ロジックは共通、Bladeレイアウトまたはテーマ変数で切り替える
  - トップページ（`/`）にはログインボタンを置かない。各サービスのトップページにのみ導線を設置
- **静的サイト側の対応**:
  - `pilates/index.html` のマイページリンクを `/pilates/login` に変更済み

### D-A-005 管理者認証の構造

- **決定**: admins / sections / admin_section

管理者は admins テーブルで一元管理し、Pilates/ThinkMotionのセクション区分は sections テーブル＋admin_section 中間テーブル（多対多）で持つ。
ガードは admin 単一。セクションごとにガードを分けない。
理由：将来的にアプリ（ピザ屋アプリ等）が増える可能性を考慮し、adminsテーブルへのスキーマ変更なしでsectionsに1行追加するだけで拡張できる設計にした。
boolean列（is_pilates_admin等）ではなく中間テーブルを選んだ理由：管理対象アプリの集合がオープンエンド（今後増える前提）であり、業務ロジックに直結するフラグ（ユーザー側のis_pilates_user等）とは性質が異なるため。

- **ユーザー側フラグとの違い**:

ユーザー側（is_pilates_user / is_client / is_medical）は固定的な3値・業務ロジック直結のためboolean列のまま。
管理者側（sections）は拡張前提のアクセス権限グルーピングのため中間テーブル。
判断基準：「集合が固定か拡張前提か」「業務ロジックの分岐条件か、権限のグルーピングか」。

- **「売却」シナリオとテーブル分割の関係**:

Pilates/ThinkMotionを同一施設の従業員・同僚と共有する程度であれば、admin/thinkmotion管理画面を別ルートにするだけで十分（テーブル分割は不要）。
「Pilates側のホームページを丸ごと買いたい」という第三者への売却は、コードベースの複製で対応する話であり、adminsテーブルの事前分割とは無関係。将来分離を見込んだテーブル設計の先回りは不要と結論。

### D-A-006 ログイン・2FAフロー

- **決定**: Pilates/ThinkMotionでログインビュー・ルートは別（/pilates/admin/login, /thinkmotion/admin/login）だが、認証処理（adminLogin）は共通メソッドで処理し、$request->is('thinkmotion', 'thinkmotion/\*') でセクション判定する。
- 判定方法はユーザー側View Composerと同じパターンに統一（ルート名判定ではなくパス判定）。
- AdminLoginRequestはauthenticate(string $section)でセクションチェックまで行う。ログイン時点のチェックはリクエストクラスで完結し、ログイン後の各ルートアクセスはadmin.sectionミドルウェアが担当する（役割分担を明確化）。
- pilates_login_from / thinkmotion_login_from はユーザー側の予約導線専用のセッションキーであり、admin側のログインフローとは独立（干渉しない）。

### D-P-001 is_paid_venue

- **決定**: 会場ごとに追加料金が発生するかどうかをbooleanの`is_paid_venue`で表現する。金額は会場マスタにデフォルト値(`price_addon_per_session`)として持たせつつ、予約単位での上書きも許容する
- **背景**: beautyRubyの¥2,000/人は交通費・場所代を区別せず一律の追加料金であり、公民館は基本追加料金が発生しない(使用料が高い会場では将来的にお客様に負担してもらう可能性はゼロではない)。ただし公民館では予約する部屋を変更する必要がある場合など、同じ会場でも金額が変わる正当なケースがある
- **理由**: 「有料/無料」の二値かつ会場デフォルト値で大半のケースはカバーできるが、部屋変更のような会場側の事情による金額変動には対応できない。フリー入力の上書きを予約単位で許容することで、例外を無理に会場マスタ側の複雑化(部屋ごとのマスタ化等)で吸収せず、実際に発生した金額をそのまま記録できる。青色申告上「交通費」と「場所代」を経費区分として分けて記帳する必要はあるが、これは会計処理側の分類の問題であり、予約システムのDB設計上は単一の`price_addon_per_session`で表現して問題ない
- **トレードオフ**: 上書きを自由記述にする分、「なぜこの予約だけ金額が違うのか」を後から追いにくくなる可能性がある。乱用を防ぐ運用ルール(誰が・いつ・なぜ変更したかの記録)は別途検討の余地あり

### D-P-001 補足(2026-07)

- **変更点**: `is_paid_venue` を `lesson_slots` から `locations` へ移動。会場単位の値のみで運用し、予約単位の上書きカラムは追加しない
- **背景**: 実費のブレ(延長料金・交通費等)は予約単位ではなく「その日全体」で発生するため、`reservations` に紐づける設計は実態と合わない
- **方針**: 実費の記録・按分は `payments`/`payment_items` 側(日単位の記帳)で扱う。予約システムのDB設計は会場マスタのデフォルト値のみで完結させる

### D-P-002 guest_pass_purchases + guest_pass_usages への分離

- **決定**: 回数券を「購入履歴」と「利用履歴」の2テーブルに分離し、残数は都度計算する
- **背景**: 当初は`guest_passes`という単一テーブルで残数をカラムとして直接持たせる設計だった
- **理由**: 残数をカラムで直接管理すると、予約キャンセルや不整合発生時に手動で数値を調整する必要が生じ、データの正当性を保証しづらい。購入と利用を分離し残数を動的計算にすることで、常に履歴から残数を再現できる(監査可能性の担保)
- **トレードオフ**: 残数取得のたびに集計クエリが必要になるため、パフォーマンスが問題になった場合はキャッシュ層の検討が必要

### D-P-003 キャンセルポリシーの一本化(¥500定額)

- **決定**: 会場や予約種別によらず、前日正午締め切り後のキャンセル料を¥500定額とする
- **背景**: 会場ごとに異なるキャンセルポリシーを設定する案もあった
- **理由**: 料金体系が複雑になるとクライアントへの説明コストが増し、運用ミスの原因にもなる。少人数運営の現状では、シンプルなルールの方が講師・クライアント双方にとって認知負荷が低い
- **トレードオフ**: 会場側の事情(公民館のキャンセル規定等)と自社ポリシーが将来乖離した場合は例外処理が必要になる可能性がある

---

### D-P-004 no_showステータスの自動ブロックなし

- **決定**: `no_show`ステータスを予約に持たせるが、一定回数での自動制限(次回予約ブロック等)は行わない
- **背景**: 無断キャンセル・当日不参加の記録機能自体は必要だが、自動化した罰則ルールにするかは別問題
- **理由**: 小規模運営では個々の事情(体調・家庭の事情等)が多様であり、機械的なルールよりも講師の目視判断を優先する方針(「小規模ゆえに人間の判断を残す」という設計思想と一致)
- **トレードオフ**: 記録が講師の確認頻度に依存するため、確認を怠ると意味をなさない。運用ルール(いつ確認するか)は別途明文化が必要

### D-P-005 CancelReservationアクションクラスへの集約

- **決定**: クライアント側・講師側それぞれのキャンセル処理を、`cancelledBy`(`client` / `teacher`)を引数に取る単一のアクションクラスに集約する
- **背景**: ユーザー側キャンセル機能を先に実装した際、キャンセル時の副作用(ステータス変更・`cancelled_at`記録・キャンセル料判定等)がコントローラに直接書かれていた
- **理由**: 管理側キャンセル機能を追加するにあたり、同じロジックを2箇所に重複させたくない。誰がキャンセルしたかによって分岐する部分(通知内容、料金判定の可否等)はあるが、コア処理は共通化できる
- **状態**: 🔧着手中。ユーザー側は実装済み、管理側実装時に抽出予定
- **トレードオフ**: 分岐ロジックが増えるとアクションクラス自体が肥大化するリスクがあるため、`client`/`admin`以外の呼び出し元が増える場合は再分割を検討

### D-P-006 通知優先度(講師への通知 > 自動クライアント通知)

- **決定**: LINE Messaging APIによる通知のうち、講師自身へのプッシュ通知を自動クライアント通知より優先して実装する
- **背景**: 通知機能は複数の宛先(講師/クライアント)・複数のトリガー(予約確定/キャンセル/リマインド等)が考えられる
- **理由**: 小規模運営では、講師が予約状況をリアルタイムに把握できることの方が、クライアントへの自動通知よりも運営上の優先度が高い(見落としによる二重予約等の実害を防ぐ)
- **トレードオフ**: クライアント向け通知(リマインド等)の実装が後回しになる分、当面は手動対応やマイページでの自己確認に依存する

### D-P-007 セッション一覧の月単位ナビゲーション

- **背景**: セッション一覧の表示方法として、リスト全件表示や週単位表示等の選択肢もあった

- **トレードオフ**: 月をまたぐ分析(トレンド確認等)には別途集計画面(分析)が必要になる

### D-P-009 管理者代行予約機能

- **背景**: クライアントから「次回新規者と一緒に来たいので枠を押さえてほしい」といった、ホームページ予約フローに乗らない依頼が発生する。この運用に対応するため、管理者が代わりに予約を確定させる機能を実装する。

- **基本方針**: Webアカウント（User）とピラティス利用者（Client）を分離する。口頭予約やメール予約のためだけにUserを作成しない。

- **対象者の分類**:
  - A. Web操作が可能な人：本人がホームページからUser登録し、Web予約を利用する。
  - B. Web操作を利用しない人：管理者がClientを登録し、代行予約を行う。User登録は不要。

- **予約方法**:
  - A. 本人がホームページで予約する。
  - B. 管理者が代行予約する（レッスン直後の予約、口頭予約、メールによる予約など）。

  予約経路の違いによってバックエンド処理を増やさず、管理者代行予約は共通の処理とする。

- **決定**:

1. **UserはWeb認証用のアカウントとし、口頭予約・メール予約のために自動生成しない。**
   - 従来の「氏名＋電話番号で仮登録Userを作成する」方針を撤回する。
   - 従来の `Hash::make(Str::random(40))` による仮登録Userのランダムパスワード生成も、新規の管理者代行予約では不要とする。
   - `users.password` はWeb認証用として必須のまま維持する。

2. **管理者代行予約では、Webアカウントを持たない人もClientとして登録できるようにする。**
   - `clients.user_id` はnullableとする方針。
   - Client作成時の `is_active` は原則falseとする。
   - 初回来店前でもClientレコードの作成を認める。
   - Clientの存在と、セッション実施済みであることを同一視しない。

3. **管理者代行予約はClientと予約枠を紐付ける設計とする。**
   - 既存Clientを検索して予約するか、新規Clientを登録して予約する。
   - 新規Client登録は顧客管理機能の責務とする。
   - 予約の作成処理は既存の `ReservationService` を可能な範囲で共通利用する。
   - 予約テーブルが現在Userを必須としている場合、Clientを基準に予約できるよう関連付けを見直す。
   - 新規者の氏名・電話番号はクライアントの情報として扱い、Userを自動生成しない。

4. **Web登録済みの人とClientを紐付けられるようにする。**
   - Web会員登録のみの時点ではClientが存在しなくてもよい。
   - Clientが後からWeb登録する場合、既存Clientと新規Userを紐付ける。
   - 氏名・電話番号・メールアドレスの一致だけで自動連携せず、本人確認の方法を設計する。

5. **流入経路（source）は記録しない。**
   - 現時点では分析目的の追加カラムを設けない（YAGNI）。

6. **管理者代行予約は `AdminReservationController` で扱う。**
   - 通常のWeb予約と管理者代行予約は、入口となるコントローラーを分離する。
   - Clientの新規登録・編集は顧客管理側で扱う。
   - `AdminReservationController` は予約枠と予約対象Clientを受け取り、予約を作成する責務を持つ。
   - 連続する複数時間枠は、従来どおり各枠に対して個別予約を作成する。
   - 予約作成UXは1枠1操作とし、一括選択機能は現時点では追加しない。

- **既存実装で変更対象となる箇所**:
  - `AdminReservationController::store()` の `UserProvisioningService::create()` 呼び出し。
  - `ReservationService::createReservation()` の `user_id` 前提。
  - `reservations` テーブルの関連付けと必須制約。
  - 既存User検索・Client検索・新規Client登録の管理画面動線。
  - Userに保存している `relationship_note` の管理先。

- **未確定事項**:
  - `reservations` テーブルとClientの具体的な関連付け方法。
  - Clientの新規登録に必要な最低限の項目。現状の `clients.gender` は必須であるため、初回予約時の入力要件を確認する。
  - 既存の仮登録UserをClientへ移行する手順。
  - Web登録時に既存Clientと安全に紐付ける本人確認方法。
  - Googleカレンダー連携における管理者アカウント数とrefresh_tokenの保存単位。

### D-P-010 クライアント管理機能

- **背景**: `users` はWeb認証を行うアカウント、`clients` はピラティス利用者を管理するレコードである。従来は初回セッション実施後にClientを作成していたが、管理者代行予約のためだけにUserを作成しない設計へ変更する。

  Clientの作成タイミングと、自主トレログの利用資格を分離する。

- **基本方針**:
  - UserとClientは独立して存在できる。
  - ClientはWebアカウントを持たなくても登録できる。
  - Clientは初回来店前から存在してよい。
  - `is_active` はClientの利用状態を表す。
  - is_active = falseは初回来店前も含むため、休止・統合済みの判定には使わない
  - 自主トレログの利用には、認証済みUserとの紐付けと有効なClient状態の両方を必要とする。

- **決定**:

1. **Clientを顧客管理の基準レコードとする。**
   - 管理者が扱うピラティス利用者は `clients` を基準に管理する。
   - 従来の「`users.is_pilates_user = true` のUser一覧をクライアント一覧とする」設計を見直す。
   - Userの有無とClientの利用状態を別々に表示・判定する。
   - `users.is_client` はClientの存在と情報が重複するため、今後の扱いを再検討する。

2. **Clientは初回予約時点で作成可能とする。**
   - 管理者代行予約では、Webアカウントを作らずにClientを登録できる。
   - 新規Clientの `user_id` はnullを許容する。
   - 初回来店前のClientは原則 `is_active = false` とする。
   - 初回来店後、管理者が利用状態を確認して `is_active = true` にする運用を基本案とする。

3. **Clientの登録フォームは必要最小限の情報を扱う。**
   - 氏名など、予約・顧客識別に必要な項目を登録する。
   - occupation、body_notes、personality_notesなどは初回登録時に必須とせず、必要に応じて追記する。
   - 現行のgender必須制約については、予約時点で取得する必要があるか再検討する。
   - 不要な個人情報を初回登録時に収集しない。

4. **自主トレログの利用資格をClientの状態とWeb認証から判定する。**
   - ログイン済みUserが存在する。
   - そのUserに紐付くClientが存在する。
   - Clientの `is_active` がtrueである。
   - 操作対象のClientが認証済みUser本人に紐付いている。

   上記を満たす場合に自主トレログの利用を許可する方針とする。単にClient IDが存在するだけでは許可しない。実際の認可はサーバー側で行う。

5. **Client管理画面の一覧対象を見直す。**
   - 従来のUser基準の一覧から、Client基準の一覧へ変更する方針。
   - Webアカウント未登録のClientも表示する。
   - 表示候補はname、phone、is_active、Webアカウント連携状態、直近予約日、line_linked、has_unpaid_fee。
   - Clientが存在しないWeb登録者を管理画面でどう扱うかは別途検討する。

6. **Clientの詳細画面と更新処理をClient基準に整理する。**
   - 現行の `PATCH /clients/{user}` はUserを前提とするため、Client IDを基準としたルーティングへの変更を検討する。
   - name、line_linked、is_activeの部分更新方式は維持する。
   - body_notes、personality_notesは従来どおり読み取り専用とし、カルテ機能で編集する。
   - ゴール設定、セッション履歴、予約履歴、初回問診、会計情報、トレーニングログの緊急メッセージ一覧は、従来の実装範囲・別タスクの区分を維持する。

7. **`is_active` とアーカイブの関係は原則維持するが、表示上の状態を区別する。**
   - `is_active = false` は自主トレログの利用資格がない状態を表す。
   - ただし、新規予約者もfalseとなるため、falseだけで「過去に利用していたが休止した人」とは判定できない。
   - 従来の `is_active = false` をそのままアーカイブ判定に使用する設計は再検討する。
   - 休止・アーカイブの管理方法は、初回来店の有無と合わせて別途決定する。

8. **個人情報の保存期間とWebアカウントの削除を分離する。**
   - Webアカウントを削除しても、Clientの保存が業務上必要な場合は独立して管理できるようにする。
   - 休眠・退会から一定期間経過後の削除または匿名化を検討する。
   - 保存義務のある記録と、不要になった認証情報・連絡先情報を区別する。
   - 具体的な保存期間、通知方法、削除処理は別途決定する。

- **既存実装で変更対象となる箇所**:
  - `clients.user_id` のnullable化。
  - Client一覧のUser基準検索・ソート。
  - `users.is_client` と `users.is_pilates_user` に依存する処理。
  - Client詳細画面のUser ID基準のルートとガード。
  - `is_active` をアーカイブ判定として使う処理。
  - 自主トレログのPolicy等の認可処理。
  - Client作成時の必須入力・バリデーション。

- **UserとClientの関係**:
  - UserとClientの関係を1対1とする
  - Web登録済みのUserと既存Clientの紐づけは、本人確認後に行う。氏名・電話番号の一致だけでは自動連携しない。

- **未確定事項**:
  - `is_active` の現在の実装上の用途と、初回来店後の変更処理。
  - 新規予約者・利用中・休止中・退会済みを区別するための状態管理。
  - 既存User・Clientデータの移行と整合性確認。
  - 退会・休眠ユーザーの保存期間と削除条件。

### D-P-012 予約時の連絡先(電話番号)入力機能

### 背景

ホームページ予約(thinkmotionと共通のregisterフロー)では電話番号を求めていないため、当日連絡がつかないケースがある。LINE登録・スタンプ返信に頼らず、確実に連絡先を確保する手段として、予約フォーム内で電話番号を収集する設計にした。

### 対象フローの整理(3系統、独立)

1. **ラインで予約**: ユーザー登録したくない人向け。Laravel側とは無関係。
2. **本登録ユーザーの予約(今回実装)**: thinkmotion共通registerでログイン済みの人。登録時に電話番号を収集していないため、予約画面で不足分を埋める
3. **口頭予約**: 管理者が代行。既存の「電話番号+氏名でのclient登録ロジック」がそのまま該当

### 決定事項

1. **代表者の電話番号はClientテーブルの`phone`カラムに一本化**。予約フォーム内に常時表示(値があればプリセット、なければ入力欄)し、`requiredIf`でClients側に値がない場合のみ必須にする。
2. **電話番号の正規化は`StoreReservationRequest::prepareForValidation()`で実施**。
   - 代表者用(`normalizePhone`): 全角数字→半角、ハイフン類(全角/半角/長音記号)を完全除去し、1本の番号文字列に統一
3. **Clients更新のタイミングはトランザクション内**。枠の重複チェック(`lockForUpdate`)後、予約作成(`create`)前に`$Client->update(['phone' => ...])`を実行し、予約作成に失敗した場合は電話番号更新もロールバックされる一貫性を優先した(選択肢(a)独立更新ではなく(b)トランザクション内包含を採用)。

- Googleフォーム送信時のLINE/メール通知(Laravelアプリ範囲外、Google Apps Script等での別途対応)

### D-T-003: ユーザー種別のフラグ管理と医療従事者判定

- **背景**:

登録画面でPilates/ThinkMotionいずれかを選択する。

- ThinkMotion選択時: 登録時点では`is_medical=false`(`is_pilates_user=false`, `is_client=false`)。プロフィール必須項目を入力しバリデーション通過後、`is_medical=true`。

- **検討過程**:

occupation(職業)の入力において、選択肢にない職種(例:メディカルソーシャルワーカーなど、医療従事者の枠に入れるべきか判断が分かれる職種)への対応を検討。

- **決定**:

occupationは固定プルダウン(医師/看護師/理学療法士/作業療法士 等)のみとする。該当項目がない場合は、プロフィール登録画面内に別途Googleフォームへの案内リンクを設置し、そちらで個別に事情を確認した上で管理者が手動対応する。

- システム側のバリデーションロジックは単純なまま維持
- 境界事例の受け皿は運用(Googleフォーム)側に切り出す
- pending画面や自由記述欄の実装は不要

### D-T-004: セッション共有(両セクション登録ユーザーの行き来)を保留

`.localhost`をワイルドカードドメイン(`SESSION_DOMAIN=.localhost`)としてCookieに設定しようとしたところ、Chromeが「現在のホストに対してDomain属性が無効」としてCookie発行自体をブロックし、ログインが機能しなくなった(419エラー)。`localhost`はブラウザにおいて分割不可の特殊ドメインとして扱われるため。

## D-T-005: 草(Contribution Graph)機能 - 表示条件

### 背景

GitHub の contribution graph を参考にしたエンゲージメント可視化を検討。
ただし GitHub 自体が「空コミットで草を埋める」現象を誘発した実例であり、
量が目的化するリスクを内包していることを前提に設計する。

### 決定事項

- **可視範囲**: ユーザー本人のみ。管理者・他ユーザーには非表示。
  - 理由: 良好な職場関係では努力は行動から伝わるため可視化は不要。
    悪い関係では監視装置に転じるリスクがある。
- **デフォルト状態**: 非表示
- **解禁条件（AND）**:
  1. 能動的アクセス条件: 振り返りページへの訪問 3回以上
  2. 記録量条件（以下いずれかを満たす、OR）:
     - 通常の投稿 5回以上
     - 症例投稿（初期仮説のみ） 5回以上
     - 症例投稿（三段階：仮説→介入→乖離分析、全て完了） 2回以上
- **マス目の質的表現**（草の色分け）:
  - 空白: 記録なし
  - 薄: ログインのみ／未完成の投稿
  - 中: 三段階まで到達
  - 濃: 過去記録への振り返り・修正あり

### 除外した案

- 管理者可視化: ユーザーの歩みが目的のため不採用
- 単一の合成スコア表示: 「スコアを上げる」ことの目的化を避けるため不採用

## D-T-006:表示可否の判定条件

- **決定事項**: 表示条件は「room_id が null」または「紐づく room.visibility が公開扱い」とする。非公開ルーム内の投稿はトップページを含むルーム外のどの画面にも一切表示しない。

- **背景**: 症例検討・Readings・My Studiesの投稿は、ルームに属さない場合と、公開/非公開ルームに属する場合の両方が存在する構造になっている。

- **理由**: 表示条件をシンプルな1つの論理式にまとめることで、クエリスコープとして1箇所に集約でき、トップページ以外の画面(将来の一覧画面など)でも同じ条件を再利用できる。

- **トレードオフ**: 「非公開ルームの存在自体は見えるが中身は見えない」といった中間的な見せ方は今回のスコープから外している。将来そうした要件が出た場合は判定条件を分岐させる必要がある。

## D-T-007:非公開ルームへのアクセス方式

- **決定事項**: 招待リンクは「ルーム単位で1つの固定リンク」方式とする。

- **背景**: 非公開ルームへの参加経路をどう設計するか(個別発行のトークンか、共有可能な固定リンクか)が論点だった。

- **理由**: 固定リンクであれば、Roomテーブルにinvite_tokenを1カラム追加するだけで済み、招待ごとの個別テーブルが不要になる。実装・運用コストが小さい。

- **トレードオフ**: リンクが漏れた場合や退会者を締め出したい場合に備え、リンクの再発行(ローテーション)機能を別途用意する必要がある。個別発行方式に比べ、誰が招待されたかの追跡はできない。

## D-T-008:型設計(フラット構造)

- **決定事項**: ArticlePost型はルーム名・投稿者名を含めてフラットな構造とし、room/authorのネストは行わない。

- **背景**: ルーム名・投稿者名もそれぞれクリックで遷移先を持つため、これらをどう型で表現するかが論点だった。

- **理由**: 現時点ではルームや投稿者を単独で扱う画面がなく、フラットな構造で表示要件を満たせる。過剰な抽象化を避け、今必要な分だけ定義する方針に合う。

- **トレードオフ**: 将来ルーム詳細ページや投稿者プロフィールページを作る際、Laravel APIのレスポンス(リレーション込みのJSON)との対応がフラット構造のままだと取りづらくなる可能性がある。その場合はネスト構造への変更が必要になる。
